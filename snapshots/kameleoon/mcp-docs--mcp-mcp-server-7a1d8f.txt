Kameleoon MCP server
Copy page
Copy page
Connect AI coding assistants directly to your Kameleoon project to automate experiment and feature flag workflows.
Copy page
Copy page
The Kameleoon Model Context Protocol (MCP) server connects AI coding assistants directly to your Kameleoon project. It enables agentic workflows for experiments and feature flags. Beyond reading configurations and pulling variation code, your AI assistant can build and manage experiments, feature flags, goals, segments, triggers, and targeting rules, and run the full rollout lifecycle, all from your development environment. Register and authenticate the server to automate your implementation lifecycle, from a winning variation to a gated production rollout.
​
Set up the server where you build
Select your AI coding assistant to get a ready-to-paste setup prompt.
Kai
, Kameleoon’s in-app AI assistant, includes these same tools natively, with no separate connection step. Use the setup prompts for your AI coding assistant when you want it to act on your Kameleoon project from your IDE instead.
If you want to use these tools from Claude or ChatGPT chat (web or desktop) rather than an IDE, see
Connect Kameleoon to Claude and ChatGPT
.
​
Features
After you connect the server, your AI agent can interact with Kameleoon to:
Discover and inspect experiments, feature flags, goals, segments, triggers, and targeting rules.
Build experiments end to end: create, duplicate, edit their settings and traffic split, add variations with their own code, and run the full lifecycle (start, pause, resume, stop, delete).
Manage feature flags: create, duplicate, delete, toggle per environment, and review the change history.
Configure flag delivery: add targeted and experimentation rules, custom variations, and typed variables.
Create and maintain goals, audience segments, and triggers, and set an experiment’s segment and trigger.
Analyze experiment and feature-flag-experiment results, and pull raw variation code (JavaScript and CSS).
Automate the full implementation lifecycle, from a winning variation to a gated production rollout.
​
Create variations with their own code
Your AI assistant can set up a test with several variations, each with its own code, without direct API calls. Give the assistant the page URL and the element selectors to change, and ask it to follow these steps:
Create the experiment with
experiment_create
, for example as a
DEVELOPER
experiment.
Use the ID of the auto-created
Variation 1
from the
experiment_create
response, and set its code with
experiment_variation_update
. Don’t add a second variation for it.
Add each further variation with
experiment_variation_create
, passing its
name
and any
jsCode
,
cssCode
,
customJson
, or
redirection
it needs.
To restrict who views the experiment, set its segment or trigger with
targeting_rule_update
. The experiment already has a targeting rule, so don’t create another one.
Read back each variation’s code with
experiment_code_get
to confirm the code that Kameleoon stored.
Kameleoon can’t recover a variation’s previous code from the server. Copy the existing code somewhere safe before you update it.
The tools store the code you provide. They don’t generate it, so the result is only as accurate as what your AI assistant knows about the page, which includes the URL and element selectors. An assistant that can read your codebase or the live page can use that context when it writes the code.
In a draft experiment, Kameleoon splits traffic evenly across the original page and all variations. With two variations, each of the three versions gets 33% of the traffic. A variation added to a running experiment starts with 0% traffic. Set its share with
experiment_traffic_allocation_set
for a paused or scheduled experiment, or in the Kameleoon app while it’s running.
Both variation tools check the experiment first. On an experiment that isn’t a draft, such as one that’s running, the tool returns a preview of what will change and applies it only after you confirm.
For example, you can use this prompt:
“On site
d1alzzxd7k
, create a developer experiment for
https://www.example.com/pricing
with two variations. Make the
#buy-now
button red in the first variation and green in the second.”

Edit experiments, segments, and triggers
Your AI assistant can change an existing experiment’s settings and targeting without the Kameleoon app. For example, a draft experiment needs a goal and a traffic split before it can start. The assistant can attach the goal, set the split, and point the experiment at the segment or trigger that should target it.
Each experiment comes with a targeting rule. The assistant changes the segment or trigger of that rule with
targeting_rule_update
, so you don’t need to create a second rule.
Changes that affect live traffic need your confirmation. When an experiment has left draft, or when you change the conditions of a segment or trigger that anything other than a draft experiment uses, the assistant first returns a preview of what will change. It applies the change only after you confirm. The MCP server can’t change the traffic split of a running, deviated, or stopped experiment, or of an experiment used as a personalization. Make that change in the Kameleoon app.
For example, you can use this prompt:
“On site
d1alzzxd7k
, for the draft experiment
Pricing test
: attach goal
Purchase
, split traffic 50/50 between the original and the variation, and target it to phone visitors on
/pricing
.”
The assistant finds the experiment and the goal, attaches the goal, sets the split, creates a segment for phone visitors and a trigger for
/pricing
, and binds both to the experiment. The experiment is then ready to start.

Analyze results and learn from past tests
Five read-only tools let the assistant check whether an experiment’s results are reliable, see how a goal is doing, find what moved it, recall earlier learnings, and pick up Ideate ideas.
Is the test healthy?
experiment_health_check_get
runs the checks of the Health tab: visit and conversion tracking, sample ratio mismatch, and overlapping exposure.
How’s a goal doing?
goal_performance_get
returns the goal’s KPIs for a period, the change against the previous period, and daily events with unusual days flagged.
Which tests moved a goal?
goal_experiment_impacts_list
lists the variations whose effect reached the site’s reliability threshold, strongest first.
Did an earlier test cover this?
takeaway_list
returns the learnings that Kameleoon records when you pause or stop an experiment.
What should the next test be?
idea_list
reads the ranked ideas PBX Ideate generated for a page, with the full variation specs.
Health checks and goal impacts depend on data that Kameleoon prepares in the background. A tool can answer that Kameleoon is still preparing the data (
PENDING
or
PREPARING
). Ask again a minute later.

The primary workflow: Winning experiment to production
The Kameleoon MCP server automates the “last mile” of implementation.
transpose_winning_experiment
fetches the winning (or manually selected) variation’s code and applies winner-decision logic in a single call, so your AI assistant doesn’t need to chain separate results and code-retrieval steps together. Without leaving the IDE, you can instruct your AI assistant to execute the following workflow:
Run
transpose_winning_experiment
to get the winning variation’s code and implementation instructions.
Convert the code into native, production-ready code (such as React components) aligned with the existing codebase.
Create a feature flag in Kameleoon and gate the new implementation behind it.
Enable and validate the feature in production.
​
Token usage and plan considerations
Connecting the Kameleoon MCP server to an AI assistant adds a small, fixed overhead: the tool schemas that describe the available actions. This overhead stays flat regardless of which plan the assistant runs on.
The token cost of a workflow comes from the work itself, not from the connection. The following factors drive usage:
The amount of data a workflow retrieves, such as full experiment configurations, variation code, or activity logs.
The amount of code the assistant generates or converts, for example when transposing a winning variation into native app code.
The number of sites or brands a single workflow touches. Duplicating and auditing experiments across three sites consumes proportionally more tokens than running the same operation on one site.
How broadly you scope a single prompt. A narrow, single-site check consumes far less than an open-ended request to review every experiment across every site.
Before you commit a team to a specific AI assistant plan, scope your expected workflows: how many sites or brands they span, how often you run them, and whether they include large data-retrieval or code-generation steps. Recurring, multi-site workflows need a plan with a larger usage allowance or context window than a plan sized for occasional, single-site prompts. Check your AI assistant provider’s plan documentation for its specific usage limits and context window size.
​
Rate limits
The MCP server has its own rate limits, applied per user, per tool, per minute. Results and analytics tools allow 10 calls per minute, write tools allow 20 to 60 calls per minute, and the list and get tools for segments, triggers, and targeting rules allow 100 calls per minute. A call over the limit returns a rate-limit error with a
retryAfterSeconds
value.
Every MCP call also goes through the Automation API gateway, so the
Automation API limits
of 50 requests per 10 seconds and 1,000 requests per hour apply underneath. These limits count against the MCP integration, not against your own API credentials. One tool call usually makes 1 to 3 API requests, and results calls make more. Normal conversational use stays well below both limits, but bulk scripts that loop over hundreds of experiments through the MCP server can reach the gateway limit.

Available tools
The server exposes the tools below, grouped by area. Each tool maps to a single, well-scoped action, so you can compose them into larger workflows (for example: read results, pull code, create a flag, add a rule, enable it).
To use the newest tool settings, such as the results breakdowns and filters or the extra segment condition types, reconnect the Kameleoon MCP server in your client. Until you reconnect, the client keeps the tool list it loaded earlier and doesn’t show the new settings.
For
experiment_results_get
,
feature_flag_experiment_results_get
, and
transpose_winning_experiment
, the
goalResults
array covers every goal attached to the experiment, which includes primary and secondary goals. Kameleoon computes a winner verdict for the primary goal only. Secondary goals return the same statistical figures as guardrail metrics, without a verdict.
experiment_results_get
and
feature_flag_experiment_results_get
accept these optional settings:
breakdown
: splits the results.
DAY
,
WEEK
, and
MONTH
show a trend over time.
HOUR
shows a trend over a
dateFrom
and
dateTo
window of at most 2 days.
DEVICE_TYPE
,
BROWSER
,
OS
, and
NEW_VISITOR
return one bucket per value. Period buckets carry audience, conversions, and conversion rate only. Improvement and reliability stay in the summary for the whole run.
filters
: a list of strings, or one string with
;
between filters. Kameleoon combines the filters with AND. Each filter has the format
DIMENSION=V1,V2
or
DIMENSION!=V1,V2
. The dimensions and values are
DEVICE_TYPE
(
DESKTOP
,
TABLET
,
PHONE
),
BROWSER
(
CHROME
,
EDGE
,
FIREFOX
,
SAFARI
,
OPERA
,
OTHERS
),
OS
(
WINDOWS
,
MAC_OS
,
I_OS
,
LINUX
,
ANDROID
,
WINDOWS_PHONE
,
OTHERS
), and
NEW_VISITOR
(
NEW
,
RETURNING
). A breakdown by
DEVICE_TYPE
can show an
OTHERS
bucket, but you can’t filter on
DEVICE_TYPE=OTHERS
.
dateFrom
and
dateTo
: a specific period, as
YYYY-MM-DD
dates in the account time zone.
dateTo
is inclusive. Set them only when you need a specific period. A narrower window gives noisier figures, so don’t call a winner from a short window.
statisticalMethod
:
FREQUENTIST
(default),
SEQUENTIAL
,
BAYESIAN
, or
CUPED
. With
BAYESIAN
,
reliabilityRate
becomes the probability to beat the reference.
CUPED
applies to whole-run figures only, and breakdown buckets stay frequentist. The tool rejects a method that your plan doesn’t include.
conversionType
:
CONVERTED
(default) counts each converting visitor once.
ALL
counts every conversion, so the rate can exceed 100%. Improvement and reliability always use
CONVERTED
.
referenceVariationId
: the variation that the others compare against. Pass a variation ID, or
0
for the original. For feature flags, pass a variation ID or key, or
0
or
off
for the off variation. The default is the experiment’s saved reference, or the original if the experiment has none.
The response states the settings it applied in
appliedOptions
and adds notes where a figure needs context. The response leaves out figures that the engine didn’t compute, for example because of too little data or a reference without conversions, and adds a note for each one.
Results compare against the reference saved on the experiment, as the results screen does. Experiments that Kameleoon builds from a prompt, and feature flag experiments whose off variation gets 0% of the traffic, don’t return improvement and reliability.
Tools that change live traffic show a preview of what will change, and apply the change only after you confirm:
feature_flag_enable
,
feature_flag_disable
, and
feature_flag_delete
: always.
feature_flag_rule_targeted_create
,
feature_flag_rule_progressive_create
, and
feature_flag_rule_experimentation_create
: when the flag is already enabled in the target environment.
experiment_update
,
experiment_variation_create
,
experiment_variation_update
, and
targeting_rule_update
: when the experiment isn’t a draft.
experiment_traffic_allocation_set
: for a scheduled or paused experiment.
segment_update
and
trigger_update
: when the conditions change and anything other than a draft experiment uses the segment or trigger. Renaming never needs confirmation.
experiment_lifecycle_update
: for
stopped
and
deleted
.
segment_delete
and
trigger_delete
refuse to delete an item that’s in use unless you set
force
. You can’t change the traffic split of a running experiment through the MCP server. Change it in the Kameleoon app. If a feature flag rule tool times out or returns a gateway error, the tool may still have created the rule. Check with
feature_flag_get
before you retry, or the retry adds a duplicate rule.

Advanced workflow: End-to-end automation
transpose_winning_experiment
covers the winner check and code retrieval in one call, but converting that code and rolling it out still benefit from an explicit system prompt. The following example targets React apps and instructs the AI agent to call the tool, then finish the implementation lifecycle: converting the code, gating it behind a new feature flag, and rolling it out, all through the MCP tools.
Paste the following prompt into your AI assistant:
You are integrating a Kameleoon A/B experiment into a production codebase by converting a Kameleoon PBX variation into maintainable native React code.
**Context**
- Experiment ID: 373001
- Mode: strict_winner_only (default) or manual_variation_conversion (Fallback variation: 1266752)
**Rules**
- Inspect the repo first and follow existing conventions (structure, styling, routing, tests, feature flags).
- Do not copy experiment code directly. Re-implement using idiomatic React (components, hooks, state).
- Do not keep experiment-specific logic (IDs, Kameleoon APIs) in production code.
- Prefer existing feature flag systems for rollout. Use the Kameleoon MCP feature-flag tools to create and gate the flag.
- Avoid DOM manipulation (no querySelector calls, MutationObserver instances, or similar direct DOM APIs).
- Do not add new dependencies unless necessary.
- Do not modify the source experiment's lifecycle (do not stop or delete it) unless explicitly asked.
- Be explicit if something is unclear.
**Workflow steps**
1. Call transpose_winning_experiment with the experiment ID and mode, and follow its returned instructions.
2. Convert the returned code to React (convert JS code to React components/hooks, and CSS code to the project styling system).
3. Create a feature flag "pbx-winning-experiment-373001" (feature_flag_create). If the implementation needs more than a simple on/off, add variations and typed variables (feature_flag_variation_create, feature_flag_variable_create, feature_flag_variation_variable_set), then gate the converted code behind the flag.
4. Roll out and validate: add a delivery rule (feature_flag_rule_targeted_create for a staged percentage rollout, or feature_flag_rule_experimentation_create to keep measuring), enable the flag in the target environment (feature_flag_enable), and confirm the final configuration with feature_flag_get.

Include the site code when you work with feature flags.
Include the experiment ID when you query experiments or experiment results.

​
General troubleshooting
​
Rate-limit error
A tool call returns a rate-limit error that includes a
retryAfterSeconds
value.
Cause:
The call went over the MCP server’s per-tool limit for your user, or the Automation API gateway limit for the MCP integration.
Fix:
Wait the number of seconds in
retryAfterSeconds
, then retry the call. For bulk work, batch your requests or throttle the loop so it stays under the limits.
​
Port 35535 is already in use
If authentication fails with an
EADDRINUSE
error, another process already listens on the OAuth callback port.
Cause:
A stale
mcp-remote
process remains active from a previous authentication attempt.
Fix:
Stop the stale process that’s using port 35535, then rerun the OAuth command.
​
MCP server doesn’t appear in Codex chat
Codex might not hot-reload newly added MCP servers into an already-running thread.
Fix:
Refresh Codex or start a new session after you update
config.toml
.
​
Browser flow doesn’t complete
If the OAuth browser window opens but authorization doesn’t finish:
Confirm that you clicked the
Authorize
button on the Kameleoon login page.
Check that your browser or system settings don’t block
localhost
callbacks.
Manually open the callback URL if your browser fails to launch it automatically.
​
A tool returns BLOCKED instead of making the change
Tools that change live traffic return a preview with the status
BLOCKED
until you confirm, which doesn’t mean an error.
Fix:
Read the preview, and if the change is what you want, ask your AI assistant to repeat the call with
confirm
set to
true
. For
segment_delete
and
trigger_delete
, use
force
instead.
​
Health check returns DOWNSTREAM_ERROR
experiment_health_check_get
fails for an experiment that uses a ratio goal whose numerator goal isn’t attached to the experiment.
Fix:
Attach the missing goal in the app, or run the check on another experiment.
​
Goal impacts return no rows
goal_experiment_impacts_list
can return no rows while the data is still preparing.
Fix:
Check the
readiness
field (
PREPARING
,
PARTIAL
, or
READY
), and ask again after
retryAfterSeconds
.
​
Single-day results differ from the daily breakdown
A one-day window follows your organization’s time zone. Daily buckets follow the site’s time zone, so the two can cover different 24 hours.
​
Improvement is 0 or missing on a variation
There’s no baseline to compare with when the original gets 0% of the traffic.
​
A page, page size, or limit of 0 returns the default
In
takeaway_list
and
goal_experiment_impacts_list
, 0 for a page, page size, or limit means “use the default.”
​
New tools are missing after a release
Clients keep the old tool list until you reconnect.
Fix:
After a release, reconnect the Kameleoon MCP connector.
​
Headless or remote agents fail to authenticate
Remote or headless agents (such as cloud-hosted Codex) can’t complete the browser-based authorization step.
Fix:
Use a desktop version of your tool instead.
​
npx
command not found
If the command fails with a “not found” error, ensure that
npx
is available on your system path. Node.js versions 8.2 and later include
npx
by default.
